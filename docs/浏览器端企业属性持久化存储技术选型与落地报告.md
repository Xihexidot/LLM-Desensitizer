# 浏览器端企业属性持久化存储技术选型与落地报告

> 版本：v1.0 ｜ 日期：2026-08-03 ｜ 适用范围：AI 输入安全助手 Chrome/Edge 插件
> 关联原型：`plugin/managed_schema.json`、`plugin/managed-store.js`、`plugin/policy/*`、`plugin/manifest.json`、`plugin/background.js`

## 1. 背景与需求

### 1.1 业务问题

浏览器端存在一类**需由用户自行填写的固定业务信息**（员工工号、所属部门、公司名称等）。此类信息当前由员工在配置面板手动填写并存入 `chrome.storage.local`，存在以下痛点：

1. **可篡改**：员工可随意修改工号/部门，绕过按部门、按身份的访问控制与审计归因；
2. **不可控**：本地存储可被清除、随浏览器数据迁移而丢失，无统一强制来源；
3. **合规风险**：员工自行填写的业务属性无企业侧背书，审计链不完整。

### 1.2 三大核心要求

| 要求 | 说明 |
|------|------|
| R1 基础安全（防篡改、防窃取） | 存储数据员工端不可篡改；读取过程不泄露给第三方 |
| R2 长期留存（跨会话、跨设备） | 跨浏览器会话；域内新设备登录后自动获得 |
| R3 隐私合规 | 符合 GDPR、个人信息保护法（PIPL）等主流规范 |

## 2. 候选方案对比

### 2.1 方案总览

| 方案 | 防篡改 | 跨会话 | 跨设备 | 合规性 | 运维成本 | 适配场景 |
|------|--------|--------|--------|--------|----------|----------|
| A. `chrome.storage.managed`（企业策略） | ★★★（只读，OS 级） | ★★★ | ★★★（域内自动下发） | ★★★ | 中（需 IT 侧配置） | 企业域内强制属性（**推荐**） |
| B. `chrome.storage.local`（现用） | ★（员工可改） | ★★★ | ★（手动迁移） | ★★ | 低 | 个人偏好、非强制信息 |
| C. `chrome.storage.sync` | ★ | ★★★ | ★★★（云同步） | ★（数据入 Google 云） | 低 | 个人跨设备偏好，**不适用企业强制属性** |
| D. IndexedDB / Web Storage | ★（页面级可改可清） | ★★（站点数据） | ★ | ★★ | 低 | 页面内大容量缓存，不适用身份属性 |
| E. 服务端会话 / HttpOnly Cookie | ★★★（服务端控制） | ★★★（会话） | ★★★（登录态） | ★★★ | 高（需自建登录体系） | 已有 SSO/账号体系时作为**补充通道** |
| F. 混合方案（A 强制 + B 兜底 + E 会话） | ★★★ | ★★★ | ★★★ | ★★★ | 中 | **最终落地**（本报告推荐） |

### 2.2 核心方案优劣势分析

#### 方案 A：chrome.storage.managed（企业策略存储）

- **原理**：扩展通过 `manifest.json` 声明 `managed_schema.json` 后，可只读访问 `chrome.storage.managed`。策略值由 OS 级通道注入——Windows 走注册表（GPO 或手动注册表）、macOS 走 MDM 描述文件（`com.apple.ManagedClient.preferences`）、Linux 走 `/etc/opt/chrome/policies/managed/*.json`。
- **优势**：
  - 扩展侧只读（`set/remove/clear` 直接报错），普通员工无 OS 管理员权限无法篡改 → 满足 R1；
  - 值在浏览器启动时读取，跨会话恒定；域内新设备由 GPO/MDM 自动下发 → 满足 R2；
  - 数据完全本地读取、不经第三方云，属性为"履行劳动合同所必需"的最小集 → 满足 R3；
  - 免费（无需自建服务）。
- **劣势**：
  - 仅 Chromium 内核浏览器支持（Chrome/Edge/Brave/Opera）；Firefox 需 native manifest 桥接；Safari/iOS/Android 不支持 → 兼容面受限；
  - 需企业 IT（域控/移动设备管理）侧配合，部署门槛高于纯前端方案；
  - 键值结构固定，无法存储复杂对象（仅限 schema 声明的标量字段）。
- **适配场景**：企业内网域管设备上强制注入的固定业务属性（工号、部门、公司名、默认网关、合规模式）。

#### 方案 B：chrome.storage.local（现状方案）

- 纯前端本地存储，实现简单；但员工可随意修改（`content.js` 读取时无法校验来源），清除浏览器数据即丢失，无企业背书。仅适合非强制信息（如用户个性化偏好）。

#### 方案 C：chrome.storage.sync

- 依赖 Google 账号云同步，跨设备方便但**数据流向第三方云端**，与企业数据主权和 GDPR/PIPL 本地化要求冲突，且不可防篡改。不适用于企业强制属性。

#### 方案 E：服务端会话 / HttpOnly Cookie

- 由后端统一颁发，服务端权威 + 防篡改最强；但需要完整的账号体系/SSO，落地成本最高，且插件在后台 Service Worker 中无法直接读取页面 Cookie（MV3 限制，需 `cookies` 权限）。

### 2.3 成本测算（估算口径：中大型企业 1,000 终端，IT 运维人天按 1,500 元/人天）

| 方案 | 一次性部署 | 持续运维（年） | 基础设施 | 合计（首年） |
|------|------------|----------------|----------|--------------|
| A. managed | 2~3 人天（GPO 模板编写 + 试点 + 灰度）；3,000~4,500 元 | 0.5 人天/季度（策略变更）；3,000 元 | 复用现网 AD/Intune/Jamf，0 元 | **6,000~7,500 元** |
| B. local | 0.5 人天（改动少）；750 元 | 0 元 | 0 元 | 750 元（但不满足 R1） |
| C. sync | 0.5 人天；750 元 | 0 元 | 需企业 G 套件（按席位计费） | 750 元 + 云席位（合规风险高） |
| E. SSO/Cookie | 20~30 人天（登录体系对接）；30,000~45,000 元 | 5~10 人天/年；7,500~15,000 元 | 需现有 IAM/SSO 平台或自建 | 40,000~60,000 元（功能远超本需求） |
| **F. 混合方案** | **A 的成本 + 0.5 人天本地兜底逻辑** | **≈ A** | **0 元** | **≈ 6,750~8,250 元** |

> 结论：纯功能需求（固定业务属性强制注入）下，方案 F（以 A 为主体）首年成本最低且完全满足三大要求；方案 E 仅在已有 SSO 且要求"属性实时以服务端为准"时引入。

## 3. chrome.storage.managed 方案可行性验证（重点）

### 3.1 原理与生效条件

企业策略值注入 `chrome.storage.managed` 需**三要素齐备**，缺一不可：

| 要素 | 文件/位置 | 作用 |
|------|-----------|------|
| ① Schema 声明 | `plugin/managed_schema.json` | 声明可推送的键名与类型（userId/department/companyName/gatewayUrl/complianceMode） |
| ② Manifest 声明 | `plugin/manifest.json` → `"storage": {"managed_schema": "managed_schema.json"}` | 无此声明 Chrome 直接拒绝发布策略（**本次审计发现此前缺失，已补齐**） |
| ③ 策略推送 | Windows GPO / Mac MDM / Linux 策略文件 | 将值写入 OS 级策略区 |

### 3.2 各平台推送路径

| 平台 | 推送方式 | 路径/机制 |
|------|----------|-----------|
| Windows | GPO（ADMX 自定义 或 注册表） | `HKLM\SOFTWARE\Policies\Google\Chrome\3rdparty\extensions\{扩展ID}\policy`（Edge 同理为 `...\Policies\Microsoft\Edge\...`），键值对即策略字段 |
| macOS | MDM 描述文件（Jamf/Intune/Kandji 下发） | `com.apple.ManagedClient.preferences` 域下 `com.google.Chrome.extensions.{扩展ID}`，Data 字段需 base64 编码 plist |
| Linux | 策略 JSON | `/etc/opt/chrome/policies/managed/ai-guard.json`（`3rdparty.extensions.{ID}` 结构） |

### 3.3 部署门槛评估

- **Windows**：已有 AD 域的环境，将 `windows-gpo.reg` 导入并转化为 ADMX 管理模板即可，1~2 人天；纯注册表方式（手动导入 reg）适合试点验证。
- **macOS**：需现有 MDM 平台（Jamf/Intune/Kandji），模板已提供，1 人天。
- **Linux**：运维直接放置 JSON 文件，门槛最低。

### 3.4 兼容性矩阵

| 浏览器 | 支持情况 | 备注 |
|--------|----------|------|
| Chrome（Win/Mac/Linux） | ✅ | 全平台支持 |
| Edge 79+ | ✅ | 注册表路径不同，模板已含 |
| Brave / Opera | ✅ | Chromium 内核 |
| Firefox | ⚠️ | 需 native manifest 桥接，本方案暂不覆盖 |
| Safari / iOS / Android | ❌ | 不支持托管存储，需服务端通道兜底 |

### 3.5 易用性评估

- 员工侧：**零感知**，无需填写任何信息，插件自动读取企业注入的工号/部门；
- IT 侧：策略模板即拿即用，灰度可按部门 OU 逐步下发；
- 开发侧：插件已有三级优先级降级链（managed > local 手动填写 > 自动生成 ID），策略缺失时自动回退，不阻断使用。

### 3.6 合规性评估（GDPR / 个人信息保护法）

| 合规点 | 依据 | 结论 |
|--------|------|------|
| 合法性基础 | PIPL 第 13 条 / GDPR Art.6(1)(b)：履行劳动合同所必需 | 工号、部门属于雇佣关系必需信息，无需另行单独同意 |
| 最小化原则 | 仅推送 5 个必要字段，无敏感个人信息 | 符合 |
| 本地处理 | 数据在终端本地读取，不经第三方云 | 符合 GDPR 数据传输与 PIPL 境内处理原则 |
| 审计留痕 | 后台以工号归因审计事件 | 有利于个人信息处理记录义务 |
| 数据主体权利 | 属性由企业统一维护，员工可通过 IT 渠道申请更正 | 可解释 |

### 4.2 验证结论

| 验证项 | 结果 | 说明 |
|--------|------|------|
| 只读语义（防篡改） | ✅ | `chrome.storage.managed` 对扩展只读，写操作抛错；值源为 OS 级注册表/MDM，员工无写权限 |
| Schema 声明完整性 | ✅ | 此前缺失的 `manifest` 声明已补齐，否则策略发布会被 Chrome 拒绝 |
| 读取与降级逻辑 | ✅ | 插件启动/事件时读取 managed，缺失时回退 local/自动 ID，不阻断 |
| 跨会话留存 | ✅ | 策略值随浏览器启动读取，会话间恒定 |
| 跨设备下发 | ✅ | 域内新设备由 GPO/MDM 自动下发 |
| 合规性 | ✅ | 见 3.6 |

### 4.3 原型验证的边界与前提

1. 需 Chrome 88+ / Edge 79+；
2. 扩展必须已安装且用户为域内账号登录设备（macOS 需 MDM 托管设备）；
3. `chrome://policy` 中扩展策略 Status 须为 OK；
4. 推送键名必须与 `managed_schema.json` 完全一致。

## 5. 最终落地方案

**采用方案 F（混合方案）：`chrome.storage.managed` 强制属性为主通道 + `chrome.storage.local` 个人补充为兜底 + 服务端会话审计关联。**

- **强制属性**（工号、部门、公司名、默认网关、合规模式）→ 企业策略注入，员工端只读、不可篡改；
- **个人补充**（个性化偏好等非强制信息）→ local 存储；
- **审计归因** → 以 managed 工号为主键，与后端审计事件关联；
- **降级策略** → managed 缺失时（非托管设备）回退 local/自动生成 ID，并在日志标记 `source=local/none`，保障功能可用性与可追溯性。

| 阶段 | 周期 | 事项 | 交付物 |

| **Phase 2 灰度推广**（2~4 周） | — | 按部门 OU 灰度下发策略；验证跨设备、跨会话；收集误配置反馈 | 灰度报告、GPO/ADMX 固化模板 |
| **Phase 3 全量上线**（1~2 周） | — | 全公司设备策略下发；插件本地兜底开关配置；监控 chrome://policy 异常占比 | 全量上线报告 |
| **Phase 4 合规运营**（持续） | — | 季度策略变更评审；个人信息处理记录审计；Firefox/Safari 场景（如有）启动 native manifest / 服务端通道评估 | 合规审计记录 |

### 决策要点（供评审）

1. 该方案**部署门槛低**（复用现有 AD/Intune/Jamf，无新增基础设施）、**兼容性明确**（Chromium 系全覆盖）、**易用性好**（员工零操作）、**合规性高**（本地处理 + 劳动合同必需 + 最小化）；
2. 主要约束：Firefox/Safari/移动端不支持托管存储——若目标受众含此类终端，需并行引入服务端会话通道（方案 E 子集）；
3. 建议将"工号=审计主键"作为硬约束写入验收标准，确保数据可归因。
