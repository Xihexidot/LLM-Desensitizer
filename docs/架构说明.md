# 架构说明

## 1. 架构目标

系统的当前定位不是一个单纯的“文本脱敏接口”，而是一个围绕大模型交互的安全中间层，负责：

1. 接收用户文本、结构化数据或文件附件
2. 解析并识别其中的敏感信息
3. 根据策略对敏感内容进行脱敏
4. 将安全内容转发给目标 LLM
5. 对 LLM 输出进行二次处理
6. 支持规则管理、供应商切换、前端可视化与插件接入

从职责上看，项目已经具备“平台化雏形”，但实现方式仍偏“单体业务服务堆叠”。

## 2. 当前总体架构

```text
[Vue 前端] ----\
                \
                 > [Spring Boot API 层] -> [编排层] -> [检测/脱敏/解析/LLM 子模块]
                /
[浏览器插件] --/

[规则管理 UI] -> [规则接口] -> [MyBatis Mapper] -> [H2/MySQL]
```

更细一点可以拆成：

```text
用户/插件
  -> Controller
  -> Manager / Proxy Service
  -> Parser / Detector / Strategy / Scenario / Client
  -> 数据库 or 外部 LLM API
```

## 3. 主要模块职责

### 3.1 API 层

职责：

- 对外暴露 REST 接口
- 做轻量参数兜底
- 调用后端核心服务

代表类：

- `DesensitizationController`
- `LlmProxyController`
- `GatewayController`
- `EnterpriseGatewayController`
- `SensitiveRuleController`
- `SensitiveDictController`
- `PluginAuditController` — 插件审计管道（检测 + 写入审计表 + 用户操作回写）

当前特点：

- Controller 相对偏薄
- 但存在重复的默认值处理、批量处理和兼容入口

### 3.2 编排层

职责：

- 串联各子模块
- 控制调用顺序
- 组装最终响应

代表类：

- `DesensitizationManager`
- `LlmProxyService`

当前特点：

- 两个类都已经演化成“大编排器”
- 既做流程控制，又做业务细节判断，还带有部分状态管理

### 3.3 敏感检测层

职责：

- 识别文本、结构化数据、二进制内容中的敏感实体
- 合并实体并输出统一结果

代表类：

- `SensitiveDetectionService`
- `RegexDetectionService`
- `RegexPatternDetector`
- `NlpDetectionService`
- `StructuredDataDetector`
- `BinaryDataDetector`
- `EntityMerger`
- `CustomPatternManager`

当前特点：

- 已经有拆分意图
- 但对外接口仍然非常宽
- 主实现 `RegexDetectionService` 仍然像一个总控入口

### 3.4 脱敏策略层

职责：

- 针对不同类型敏感实体或不同业务目标执行替换

代表类：

- `DesensitizationStrategy`
- `MaskDesensitizationStrategy`
- `PartialDesensitizationStrategy`
- `GeneralizationDesensitizationStrategy`
- `SemanticDesensitizationStrategy`
- `SemanticPlaceholderStrategy`

当前特点：

- 已经有比较合理的策略模式雏形
- 但策略选择逻辑还在 `DesensitizationManager` 中
- `SemanticPlaceholderStrategy` 同时被编排层直接使用，说明“业务流程策略”与“基础脱敏策略”界面还没完全分开

### 3.5 数据解析层

职责：

- 将文本、JSON/XML、PDF、DOCX、Excel 等输入统一转成可检测文本

代表类：

- `DataParserManager`
- `DataParserServiceImpl`

当前特点：

- 入口简单清晰
- 实现类承担所有格式解析
- 部分解析仍是占位逻辑，例如图片 OCR、音频识别、旧版 DOC

### 3.6 情景感知层

职责：

- 根据上下文判断当前业务情景
- 调整敏感类型范围、阈值、严格模式

代表类：

- `KeywordBasedScenarioPerceptionService`
- `LlmBasedScenarioPerceptionService`
- `ScenarioAnalysisResult`

当前特点：

- 设计方向合理
- 但主流程当前被禁用
- 造成“依赖存在、能力存在、实际不生效”的状态

### 3.7 LLM 适配层

职责：

- 屏蔽不同供应商 API 差异
- 提供统一调用接口

代表类：

- `LlmClient`
- `DeepSeekClient`
- `OpenAIClient`
- `QwenClient`
- `DoubaoClient`
- `KimiClient`
- `HunyuanClient`
- `OllamaClient`
- `LlmConfigService`

当前特点：

- 方向正确，适配器模式清晰
- 配置服务仍偏手工堆字段方式
- 还没有形成更统一的 provider registry

### 3.8 规则持久化层

职责：

- 将自定义正则规则存储到数据库
- 启动时加载到内存
- 支持启用、禁用、更新、删除

代表类：

- `SensitiveRuleService`
- `SensitiveRuleMapper`
- `SensitiveRuleMapper.xml`

当前特点：

- 数据库与内存规则已经形成双层机制
- 这是项目里相对完整的一条业务链

### 3.9 企业版网关服务层

职责：

- 接收标准化网关请求
- 委托脱敏、决策、路由流程
- 返回统一网关响应

代表类：

- `EnterpriseGatewayApplicationService`
- `EnterpriseGatewayApplicationServiceImpl`

相关实体在 `entity/gateway/` 下：

- `GatewayRequest` / `GatewayResponse`：统一网关协议
- `GatewayRiskDecision`：风险决策结果
- `GatewayInvocationContext`：调用上下文
- `GatewayAuditEvent`：审计事件

当前特点：

- 控制器已完整实现 `gateway/v1` 接口
- 服务实现为骨架，决策链尚未完整对接检测与脱敏引擎

### 3.10 前端展示层

职责：

- 提供脱敏和 LLM 交互界面
- 展示检测结果、历史记录、图表、规则管理

代表文件：

- `App.vue`
- `LlmDesensitization.vue`
- `SensitiveRules.vue`
- `Sidebar.vue`
- `ConversationHistory.vue`
- `DashboardStats.vue`
- `LlmDetectionResults.vue`
- `LlmFeatureCards.vue`
- `LlmProcessingProgress.vue`
- `LlmResultsPanel.vue`

当前特点：

- 页面功能丰富
- 但组件边界不够清晰
- `LlmDesensitization.vue` 和 `App.vue` 过重

## 4. 核心调用链

### 4.1 纯脱敏调用链

```text
客户端
  -> DesensitizationController
  -> DesensitizationManager
  -> DataParserManager
  -> SensitiveDetectionService
  -> DesensitizationStrategy
  -> DesensitizationResponse
```

流程说明：

1. Controller 接收请求并补默认值
2. `DesensitizationManager` 解析原始输入
3. 统一文本进入检测服务
4. 选择对应策略执行脱敏
5. 返回脱敏内容和检测实体

### 4.2 LLM 代理调用链

```text
客户端 / 插件
  -> LlmProxyController 或 GatewayController
  -> LlmProxyService
  -> DesensitizationRequest 构建
  -> 脱敏 / 语义扫描 / 占位符处理
  -> LlmClient(具体供应商)
  -> 响应恢复与封装
  -> LlmResponse
```

流程说明：

1. 接收 LLM 请求
2. 根据数据类型构建统一脱敏请求
3. 执行输入安全处理
4. 调用具体供应商客户端
5. 恢复或再次处理输出
6. 返回给前端或网关调用方

### 4.3 规则管理调用链

```text
SensitiveRules.vue
  -> SensitiveRuleController
  -> SensitiveRuleService
  -> SensitiveRuleMapper
  -> sensitive_rules 表
  -> CustomPatternManager / SensitiveDetectionService
```

流程说明：

1. 前端新增或更新规则
2. 后端校验正则合法性
3. 持久化到数据库
4. 同步刷新到内存规则集合

## 5. 现阶段架构问题

### 5.1 编排层过胖

`DesensitizationManager` 和 `LlmProxyService` 当前都承担了：

- 请求转换
- 主流程控制
- 默认值策略
- 条件判断
- 结果组装
- 部分业务策略

这会带来：

- 代码阅读成本高
- 单元测试难切
- 新功能继续堆进去会越来越乱

### 5.2 抽象边界不稳

典型表现：

- `SensitiveDetectionService` 方法过多，说明“检测引擎”的边界过宽
- `DesensitizationRequest` 同时承载文本、结构化、二进制三种模式
- `LlmProxyService` 既依赖 `DesensitizationManager`，又直接依赖 `NlpScanner` 和 `SemanticPlaceholderStrategy`

这说明当前并不是“明确分层”，而是“分层 + 跨层直连”混用。

### 5.3 情景感知处于半接入状态

问题不在于有没有实现，而在于：

- 服务已经存在
- 依赖已经注入
- 前端也暴露了配置
- 但后端主链路实际关闭了这段逻辑

结果就是：

- 阅读者会误以为这条链路可用
- 重构时很难判断哪些是真正有效逻辑

### 5.4 前端组件职责过载

`LlmDesensitization.vue` 当前集成了：

- 提供商加载
- 脱敏策略选择
- 附件上传与解析
- 进度动画
- 脱敏请求
- LLM 请求
- Markdown 渲染
- 导出 PDF / Markdown
- 截图分享
- 打字机效果

这类组件短期能跑，长期很难维护。

### 5.5 配置和扩展方式偏硬编码

`LlmConfigService` 中每个 provider 都有一组字段和初始化逻辑，问题是：

- 扩一个 provider 需要改多处
- 无法天然支持配置列表化
- 也不利于环境切换和动态装配

### 5.6 存在“实验性代码进入主链路”的迹象

从当前代码可以看出：

- 有大段注释保留的旧逻辑
- 有部分占位实现仍直接参与主模块
- 有些方法名和参数已经不一致

这会让系统在继续迭代时更容易出现“逻辑看起来存在，但实际上不可用”的情况。

## 6. 建议的目标架构

建议把当前单体服务重构成“清晰的 6 层协作”：

```text
API Layer
  -> Application Layer
  -> Domain Service Layer
  -> Infrastructure Layer
  -> External Adapter Layer
  -> Presentation Layer
```

落到本项目可对应为：

### 6.1 API Layer

- 保留 Controller
- 只做参数转换与响应输出
- 不承担业务兜底判断

### 6.2 Application Layer

- 新建用例服务
- 例如：
  - `ProcessDesensitizationUseCase`
  - `ProcessLlmProxyUseCase`
  - `ManageSensitiveRuleUseCase`

作用：

- 组织一条业务用例
- 调用多个领域服务

### 6.3 Domain Service Layer

拆成明确能力服务：

- `InputNormalizationService`
- `SensitiveDetectionEngine`
- `DesensitizationEngine`
- `ScenarioDecisionService`
- `LlmGatewayService`

让 `Manager` 不再成为总垃圾桶。

### 6.4 Infrastructure Layer

- MyBatis Mapper
- 数据库
- 文件解析器
- HanLP / OCR / 音频识别

### 6.5 External Adapter Layer

- `LlmClient` 各厂商适配器
- 浏览器插件网关

### 6.6 Presentation Layer

前端拆分为：

- 页面容器组件
- 表单组件
- 结果展示组件
- 历史记录组件
- composables 状态逻辑

## 7. 推荐的重构切入顺序

### 第一步：先拆编排，不先动算法

先把：

- `DesensitizationManager`
- `LlmProxyService`

拆成若干更小的 application service。

原因：

- 这是当前复杂度最高的地方
- 拆这里可以最快降低阅读和修改成本

### 第二步：收缩检测接口

把 `SensitiveDetectionService` 按输入类型拆分成：

- `TextSensitiveDetectionService`
- `StructuredSensitiveDetectionService`
- `BinarySensitiveDetectionService`

对外再保留一个 facade 即可。

### 第三步：把请求对象分型

把 `DesensitizationRequest` 拆为：

- `TextDesensitizationCommand`
- `StructuredDesensitizationCommand`
- `BinaryDesensitizationCommand`

减少状态组合爆炸。

### 第四步：拆前端巨型组件

优先拆 `LlmDesensitization.vue`：

- `ProviderSelector`
- `StrategySelector`
- `AttachmentUploader`
- `ProcessingProgress`
- `ResultComparison`
- `LlmResponsePanel`
- `useLlmDesensitization()`

### 第五步：恢复或清理情景感知

二选一：

1. 彻底恢复接入并补测试
2. 暂时完全移除依赖，等后续再加

不要继续保持半接入状态。

## 8. 当前架构结论

当前项目不是“没有架构”，而是已经形成了：

- 控制器层
- 编排层
- 检测层
- 策略层
- 解析层
- 供应商适配层
- 前端展示层

但问题在于：

- 分层已经出现
- 边界还不稳定
- 编排层承担过多职责
- 前端和后端都存在核心大文件

因此最合适的下一步不是立即全量重写，而是：

1. 先根据职责拆小核心类
2. 再对抽象接口做收缩
3. 最后再做目录和模块级重组

这会比一次性“推倒重来”风险更小，也更符合当前代码现状。
