# 在线拦截、脱敏、阻断与审计设计

## 1. 文档目标

这份文档专门回答一个落地问题：

- 当员工误把敏感信息发送给大模型时，系统如何在线完成拦截、脱敏、阻断和审计

它不是讲算法细节，而是讲企业系统在真实流量中的工作方式。

## 2. 目标问题

在企业环境中，常见风险不是“攻击者入侵模型”，而是：

- 员工误把客户数据粘贴给外部大模型
- 业务系统把生产数据原样发送给大模型
- Agent 在多轮上下文里组合出敏感信息
- 模型输出中再次回显敏感内容

企业需要的不是一个“事后看报告”的工具，而是一个在线生效的治理系统。

因此，系统必须具备以下能力：

- 在线接管大模型调用流量
- 在请求发出前做检测和决策
- 在需要时自动脱敏或直接阻断
- 在返回结果前做输出审查
- 全链路保留审计记录

## 3. 典型场景

以一个最典型的企业场景为例：

- 客服员工在浏览器中使用外部大模型
- 输入内容包含客户姓名、手机号、身份证、地址、订单号
- 企业不允许这些明文直接发送到外部模型

系统的目标不是简单记录，而是在线做出策略处理。

## 4. 在线处理总流程

```text
员工 / 浏览器插件 / 业务系统
  -> 企业 AI 安全网关
  -> 请求接入层
  -> 身份与应用识别
  -> 请求标准化
  -> 输入解析
  -> 敏感检测
  -> 风险决策引擎
     -> 放行
     -> 脱敏后放行
     -> 路由到内部模型
     -> 阻断
     -> 审批 / 复核
  -> LLM 转发层
  -> 输出审查
  -> 响应处理
  -> 审计日志 / 指标 / 告警
```

## 7. 在线决策动作说明

在线治理不是“只识别”，而是做出具体动作。

### 7.1 放行

适用：

- 未命中敏感信息
- 命中低风险可公开字段

系统行为：

- 直接转发请求
- 正常记录审计

### 7.2 自动脱敏后放行

适用：

- 命中手机号、身份证、地址、邮箱、工号等可替换字段
- 脱敏后仍能满足模型使用目的

系统行为：

- 替换原始内容
- 保留必要业务语义
- 转发脱敏后的请求

### 7.3 强制改走内部模型

适用：

- 内容较敏感，但业务必须继续
- 企业不允许将该类数据发往外部模型

系统行为：

- 不再调用公有云模型
- 自动路由到企业内网模型
- 审计中标记“跨境受限 / 对外受限”

### 7.4 阻断

适用：

- 高危数据
- 明显违规数据
- 命中禁止外发策略

系统行为：

- 不再调用任何外部模型
- 直接返回阻断结果
- 记录高优先级审计事件

### 7.5 审批 / 人工复核

适用：

- 高价值业务且系统无法自动判定
- 敏感文档上传场景
- 法务、财务、医疗等强监管场景

系统行为：

- 请求进入审批或任务队列
- 不立即发送给模型

## 8. 审计设计

在线治理必须自带审计能力，否则企业无法证明系统有效。

### 8.1 审计最小字段

建议最少记录：

- `eventId`
- `timestamp`
- `tenantId`
- `appId`
- `userId`
- `department`
- `channel`
- `requestType`
- `targetModel`
- `targetProvider`
- `sceneCode`
- `matchedSensitiveTypes`
- `decisionAction`
- `policyId`
- `policyVersion`
- `inputRiskLevel`
- `outputRiskLevel`
- `requestHash`
- `responseHash`

### 8.2 审计内容注意事项

不同于早期设计，当前实现采用了"完整记录"策略：

**当前实现**：审计表 `gateway_audit_event` 记录完整原文（`original_content`）和脱敏后内容（`processed_content`），供管理员安全审查。这是基于以下考虑：

- 安全审计需要追溯完整上下文，不能只看哈希和标签
- 管理员审查权限受控制台访问限制
- 脱敏后内容同时也保留，用于对比审查

### 8.3 当前实现的具体审计管道

**数据库**：

- 表：`gateway_audit_event`（20+ 字段，含 original_content / processed_content / user_action / target_provider）
- 仓储：`GatewayAuditRepository(Impl)` — JdbcTemplate 实现

**两个写入入口**：

1. `PluginAuditController` (`POST /plugin/audit-check`) — 浏览器插件拦截后写入
2. `EnterpriseGatewayApplicationServiceImpl.buildAuditEvent()` — API 网关调用后写入

**用户操作回写**：

- `POST /plugin/confirm-action` — 用户在弹窗中选择后，回写 `userAction` 字段（DESENSITIZE_AND_SEND / SEND_ORIGINAL / CANCEL）

**管理员审查**：

- `GET /gateway/v1/audit/stats` — 统计聚合（按渠道/风险/决策/目标LLM/用户操作）
- `GET /gateway/v1/audit/events` — 事件列表（支持 userId/appId/decisionAction 筛选）
- `GET /gateway/v1/audit/events/{eventId}` — 单条详情（含完整原文供审查）
- 前端 Dashboard / AuditList / AuditDetail 提供可视化审查界面

## 9. 企业上线建议

在线拦截能力不建议一开始就全量强制启用。

推荐分三步：

### 9.1 观察期

- 只接管流量
- 只做检测和审计
- 不阻断

目标：

- 先摸清真实数据流和误报情况

### 9.2 脱敏期

- 对中低风险内容自动脱敏
- 高风险先告警

目标：

- 让业务适应系统接管
- 验证治理效果

### 9.3 阻断期

- 对高危内容直接阻断
- 对监管场景启用审批

目标：

- 正式形成强控制能力

## 10. 与当前项目的关系

当前项目已从原型显著演进，以下模块已具备企业级基础：

- `PluginAuditController` + `plugin/content.js` → 浏览器插件审计管道（检测→写入审计→用户操作回写）
- `GatewayAuditRepository(Impl)` → JdbcTemplate 持久化审计，支持多维度查询和统计
- `EnterpriseGatewayController` → 统一网关入口（chat + structured + files + audit/events + audit/stats + audit/events/{id}）
- `LlmProxyService` → 在线转发与路由编排核心
- `DesensitizationManager` → 输入检测和脱敏引擎
- `DashboardStats.vue` / `AuditList.vue` / `AuditDetail.vue` → 管理员审查控制台
- `RiskPolicy.vue` / `DictManagement.vue` / `SensitiveRules.vue` → 策略可配置
- `ProviderStatus.vue` → 外部 LLM 调用监控
- `plugin/` → 浏览器入口（10 个平台域名检测 + 目标 LLM 识别）

还缺少的关键企业能力包括：

- 应用级鉴权
- 多租户
- 风险决策引擎与前端策略配置的在线联动（当前 buildRiskDecision 仍为硬编码）
- 输出治理策略
- 指标与告警（WebSocket 实时推送）
- 灰度与审批机制

## 11. 结论

“员工误传敏感信息”这个问题，企业真正需要的是：

- `在线治理`

而不是：

- `事后看报表`

因此，系统的价值不只是“识别到敏感字段”，而是完整完成：

1. 在线接管流量
2. 输入检测
3. 自动脱敏或阻断
4. 输出复查
5. 全链路审计

这才是企业级 AI 安全网关最核心的落地能力。
