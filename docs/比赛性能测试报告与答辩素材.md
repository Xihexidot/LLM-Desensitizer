# 比赛性能测试报告与答辩素材

> 项目：ApiSensitivities（LLM 输入输出脱敏与识别）  
> 报告日期：2026-08-15  
> 适用场景：比赛材料提交、现场答辩、赛前复测

## 1. 测试背景

本项目的核心目标不是单纯完成文本处理，而是在企业员工调用外部大模型的场景下，实现“敏感信息识别、分级脱敏、风险判定、审计留痕、监控分析”的全链路闭环。因此，性能测试不能只看单个接口的平均响应时间，而必须覆盖以下核心业务流程：

1. 文本进入系统后的实时脱敏链路
2. 浏览器插件提交审计检查后的风险判定链路
3. 安全监控看板对审计数据的聚合分析链路

本轮工作围绕比赛评审要求，完成了性能测试方案补齐、测试资产落地、真实性能数据采集、问题清单梳理以及答辩说明逻辑整理。

## 3. 数据集来源与合规说明

### 3.1 短文本数据集

- 文件：`src/test/resources/my_pii_test_set.json`
- 来源：项目内部程序化生成的合成 PII 测试集，不含真实个人数据
- 授权情况：为项目自建测试数据，无外部商业授权限制
- 数据规模：`500` 条短文本样本
- 样本特征：
  - `person=500`
  - `phone=375`
  - `bank_card=98`
  - `id_number=83`
  - `email=81`
  - `address=43`
  - `license_plate=39`
  - `passport=36`
- 业务匹配性：覆盖企业常见输入内容，如联系人信息、证件号、邮箱、银行卡、地址等，符合“员工将业务文本提交给大模型前需脱敏”的比赛业务场景

### 3.2 攻防测试集

- 文件：`src/test/resources/security_attack_test_set.json`
- 来源：基于 OWASP Top 10、OWASP LLM Top 10 和公开安全案例提炼形成
- 授权情况：来源于公开安全知识与自建样例，不含受限商业数据
- 数据规模：`12` 条攻防场景
- 类别分布：
  - `DATA_LEAK=6`
  - `ACCESS_CONTROL=2`
  - `INJECTION=2`
  - `XSS=1`
  - `OBFUSCATION=1`
- 业务匹配性：用于验证比赛场景下“敏感信息外泄、越权、注入、绕过检测”等高风险输入

### 3.3 长文本压测样本

- 文件：`src/main/resources/static/sample_sensitive_30k.txt`
- 来源：由多种合成敏感字段样例重复扩展而成
- 授权情况：项目自建，无额外授权要求
- 样本规模：`9101` 字符（当前性能测试实际读取长度）
- 业务匹配性：模拟日志片段、工单摘要、客户资料汇总、批量文本清洗等长文本处理场景

### 3.4 审计聚合样本

- 来源：测试过程中向 `gateway_audit_event` 注入受控审计事件
- 数据规模：`1200` 条
- 字段覆盖：`user_id`、`department`、`channel`、`target_provider`、`decision_action`、`input_risk_level`
- 业务匹配性：模拟比赛现场监控看板中的“多平台调用统计、风险趋势、异常识别”场景

当前性能执行环境以本地可复现为目标，和生产/比赛展示环境相比仍存在差异：

1. 当前聚合查询使用 H2 内存库，未完全等价于 MySQL 持久化环境
2. 当前主链路性能数据未叠加真实外部 LLM 网络调用时延
3. 当前未引入独立压测机与网关代理层，仍属于单机基线测试

因此，本报告中的结果定位为“核心链路基线性能结果 + 现场压测执行方案”，适合支撑比赛答辩，但赛前仍建议在准生产环境补跑一次 JMeter 全链路测试。

## 5. 工具选型与实施方式

### 5.1 工具选型

| 工具 | 用途 | 本轮状态 |
| --- | --- | --- |
| JMeter | HTTP 接口并发压测、梯度加压、聚合报告 | 已补齐计划文件与执行脚本 |

3. 监控模块已有 Playwright 与后端聚合压力测试基础，可形成交叉验证

### 6.2 指标阈值设定

| 指标 | 目标阈值 | 设定依据 |
| --- | --- | --- |
| 文本脱敏平均响应时间 | `< 5ms`（短文本） | 比赛演示时需满足实时交互体验 |
| 文本脱敏 P95 | `< 10ms` | 保证高并发下尾延迟稳定 |
| 长文本平均处理时间 | `< 200ms` | 满足长文本批量脱敏可展示性 |
| 吞吐量 | `> 30000 chars/s` | 支撑比赛场景下高频文本提交 |
| 监控 overview P95 | `< 1500ms` | 看板首屏与手动刷新需快速反馈 |
| 错误率 | `= 0` 或接近 0 | 安全链路不允许频繁失败 |
| CPU 使用率 | `< 70%` | 留足比赛现场余量 |
| 内存占用 | 无持续增长 | 避免连续演示期间堆积 |

## 8. 实际性能结果

### 8.1 S1 文本脱敏主链路

来源：`logs/perf_result_20260815_210517.log`

| 指标 | 实测值 | 目标 | 结论 |
| --- | ---: | ---: | --- |
| 短文本调用次数 | 10000 次 | - | 完成 |
| 平均响应时间 | 575.5 us | < 5000 us | 达标 |
| P50 | 232 us | - | 达标 |
| P95 | 1635 us | < 10000 us | 达标 |
| P99 | 2626 us | 关注尾延迟 | 达标 |
| 最大值 | 11502 us | - | 可接受，存在偶发抖动 |
| 长文本平均耗时 | 29.3 ms | < 200 ms | 达标 |
| 长文本最大耗时 | 37 ms | - | 达标 |
| 吞吐量 | 310614.3 字符/秒 | > 30000 | 达标 |
| 进程 CPU 占用 | 6.0% | < 70% | 达标 |
| GC 增量 | 12 次 / 30 ms | 无异常长停顿 | 达标 |
| 错误率 | 0 | 0 | 达标 |

分析结论：

1. 短文本场景已经具备比赛演示所需的实时处理能力
2. 长文本处理平均仅 29.3ms，说明规则识别和脱敏链路在当前单机场景下性能充足
3. P99 和最大值之间仍存在抖动差距，表明 JVM 垃圾回收和调度抖动仍是尾延迟风险点

### 8.2 S3 监控聚合链路

来源：`logs/monitor_perf_result_20260815_210518.log`

| 指标 | 实测值 | 目标 | 结论 |
| --- | ---: | ---: | --- |
| 审计样本规模 | 1200 条 | 千级 | 达标 |
| overview avg | 7.8 ms | < 1500 ms | 达标 |
| overview P95 | 13 ms | < 1500 ms | 达标 |
| overview max | 14 ms | - | 达标 |
| byProvider avg | 0.0 ms | < 1500 ms | 达标 |
| trend avg | 0.0 ms | < 1500 ms | 达标 |
| anomalies avg | 0.0 ms | < 1500 ms | 达标 |
| 错误率 | 0 | 0 | 达标 |

分析结论：

1. 看板端最关键的聚合查询链路在千级数据量下响应非常快
2. 当前瓶颈不在查询聚合逻辑，而更可能在未来切换到 MySQL、增加索引复杂度和扩大历史数据量之后出现

### 8.3 历史性能佐证

结合已有文档 [LLM调用监控测试报告](file:///E:/Java/Llm输入输出脱敏与识别/docs/LLM调用监控测试报告.md) 中的结果：

- 千级聚合数据加载前端首屏渲染约 `1.3s ~ 1.4s`
- 后端聚合接口在既有方案中预算 `< 3s`

这说明项目在“后端聚合 + 前端展示”层面已有历史验证，本轮新增结果则进一步把“脱敏主链路 + 监控聚合链路”的核心指标补齐了。

## 11. 比赛现场答辩说明逻辑

建议现场按“数据来源 -> 数据准备 -> 指标设定 -> 结果与整改”的顺序讲，不要一上来只报响应时间。

### 11.1 第一部分：数据集来源

标准话术：

“本项目的性能测试没有直接使用真实用户隐私数据，而是构建了可追溯的合成测试集。短文本数据集位于 `my_pii_test_set.json`，共 500 条样本，覆盖姓名、手机号、身份证、银行卡、邮箱、地址等核心敏感类型；攻防测试集共 12 条，来源于 OWASP Top 10、OWASP LLM Top 10 以及公开安全案例；长文本样本位于 `sample_sensitive_30k.txt`，用于模拟日志、工单和批量资料清洗场景。所有数据均为自建或公开知识提炼，不存在额外商业授权风险。” 

### 11.2 第二部分：性能测试数据准备

标准话术：

“我们将测试数据分为三层。第一层是 500 条短文本，用于模拟员工高频提交的实时脱敏请求；第二层是约 9100 字符的长文本，用于模拟日志和报告类批量脱敏；第三层是 1200 条受控审计事件，用于模拟监控看板中的统计聚合场景。所有样本中的敏感字段都经过显式标注，既可以做正确性验证，也可以做性能测试。在测试过程中，我们同步采集响应时间、P95/P99、吞吐量、错误率、CPU、堆内存和 GC 变化等核心观测数据。” 

### 11.3 第三部分：指标设定与达成情况

标准话术：

“指标设定遵循比赛演示的可用性要求。对于短文本实时脱敏，我们要求平均响应时间小于 5ms、P95 小于 10ms；对于长文本处理，我们要求平均耗时小于 200ms；对于监控看板聚合接口，我们要求 P95 小于 1.5s；同时要求错误率为 0，CPU 保持在 70% 以下。实际测试中，短文本平均响应时间为 575.5 微秒，P95 为 1635 微秒；长文本平均处理时间为 29.3ms；监控 overview 接口 P95 为 13ms；CPU 平均占用约 6%，整体满足比赛展示要求。” 

### 11.4 第四部分：问题识别与整改闭环

标准话术：

“我们没有把性能测试停留在‘能跑通’这个层面，而是进一步识别了三类问题：第一，历史性能测试更偏局部，缺少专业压测工具资产；第二，测试环境与生产环境存在差异，尤其是 H2 与 MySQL、Mock 与真实 LLM 时延之间的差异；第三，指标维度过去偏粗，缺少 CPU、内存、GC 和尾延迟分析。针对这些问题，我们已经补充了 JMeter 测试计划、性能基线测试代码、问题清单和整改路径，后续可在比赛机器上一键复跑。” 

## 12. 最终结论

本轮性能测试工作的结论如下：

1. 已补齐覆盖核心业务流程的性能测试方案和仓内执行资产
2. 已实际执行脱敏主链路与监控聚合链路性能测试，并形成可追溯日志
3. 当前核心指标均达到比赛展示要求，尤其是实时脱敏和监控聚合性能表现良好
4. 已识别出环境差异、专业工具执行环境、真实外部 LLM 时延等残余问题，并形成明确整改路径

综合判断：项目当前已具备比赛答辩所需的性能测试材料基础，建议赛前在准生产环境再补跑一次 JMeter 全链路测试，用于进一步增强专业说服力。
