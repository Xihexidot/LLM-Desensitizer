# 企业版目标架构图与模块边界

## 1. 文档目标

这份文档的目的不是重复“企业为什么需要 AI 安全网关”，而是进一步回答：

1. 企业版系统最终应该长成什么架构
2. 控制面和数据面分别负责什么
3. 每个模块的职责边界在哪里
4. 当前项目代码分别对应到哪个目标模块
5. 后续重构时应该按什么顺序落地

这份文档适合用于：

- 方案设计
- 比赛答辩
- 系统拆模块
- 后续代码重构指导

## 2. 总体目标

企业版目标不是“增强一个演示网站”，而是把当前项目演进为：

- `企业 AI 安全网关`
- `策略控制台`
- `审计与观测平台`

它的核心职责是：

- 统一接管企业内部所有大模型调用链路
- 对输入做解析、检测、脱敏、阻断和路由
- 对输出做二次审查和风险控制
- 对全过程做审计、告警和统计

### 3.2 分层说明

从大的边界上看，系统可以拆成 5 层：

1. `接入层`
2. `控制面`
3. `数据面`
4. `外部模型适配层`
5. `基础设施层`

## 4. 接入层边界

接入层负责承接各种调用来源，但不负责安全决策本身。

### 4.1 浏览器插件接入

职责：

- 接管网页 AI 工具请求入口
- 将流量导向企业网关
- 保持用户原操作方式尽量不变

边界：

- 只负责入口接管
- 不应在插件端做复杂安全判断
- 核心策略仍应在服务端网关执行

### 4.2 业务系统 API 接入

职责：

- 作为企业内部系统调用 AI 的标准入口
- 传递应用身份、用户身份、场景上下文

边界：

- 业务系统负责提供明确上下文
- 不负责最终风险判断

### 4.3 Agent / RAG / Workflow 接入

职责：

- 统一将 prompt、tool input、tool output、memory、retrieval chunk 纳入治理链路

边界：

- Agent 平台负责业务编排
- 网关负责安全治理

## 5. 控制面模块边界

控制面主要解决“管控”和“治理”，不直接承接高频在线流量。

### 5.1 策略中心

职责：

- 定义放行、脱敏、阻断、审批、改路由规则
- 按应用、场景、租户、部门进行策略匹配
- 支持策略版本管理与灰度发布

输入：

- 管理员配置
- 合规要求
- 场景模板

输出：

- 数据面可执行策略

边界：

- 只定义策略，不执行检测
- 不直接处理在线流量

### 5.2 规则中心

职责：

- 管理敏感规则、词典、模式、类型映射
- 维护自定义规则和内置规则

边界：

- 规则中心是知识源
- 检测引擎才是执行者

### 5.3 应用接入中心

职责：

- 注册应用
- 分配密钥
- 绑定默认策略
- 维护渠道、环境和租户信息

边界：

- 管理接入身份
- 不参与具体内容检测

### 5.4 审计查询中心

职责：

- 查询事件日志
- 提供审计报表
- 关联策略、用户、应用和命中记录

边界：

- 审计中心只读分析为主
- 审计写入应由数据面完成

### 5.5 配置中心

职责：

- 下发模型配置
- 下发路由规则
- 下发限流配置
- 下发环境参数

边界：

- 配置中心提供配置
- 数据面负责读取和执行

### 5.6 仪表盘与运营中心

职责：

- 统计命中率、阻断率、调用量、模型成本
- 查看高风险事件排行
- 观察误报和漏报趋势

边界：

- 用于运营和分析
- 不进入实时主链路

**当前实现**：

- `DashboardStats.vue` — 首页仪表盘（4 指标卡 + 饼图 + 最近审计事件表格），10s 自动刷新
- 侧边栏 7 入口导航：仪表盘 / 审计日志 / 风险策略 / 敏感规则 / 词典管理 / 调用监控 / 脱敏测试
- `RiskPolicy.vue` — 可编辑场景策略矩阵（增删改 + Toggle 启用/禁用）
- `DictManagement.vue` — 词典管理（4 类型切换 + CRUD + 热重载）

## 6. 数据面模块边界

数据面是真正承接在线请求和执行治理动作的核心。

### 6.1 接入认证模块

职责：

- 校验 token、appId、tenantId
- 识别调用来源
- 注入基础上下文

输入：

- 请求头
- 调用方身份信息

输出：

- 标准化身份上下文

边界：

- 只做身份识别和接入校验
- 不做内容判断

### 6.2 请求标准化模块

职责：

- 将不同入口的请求统一转换成标准网关请求对象
- 兼容浏览器插件、OpenAI 协议、业务系统自定义协议

输入：

- 原始请求

输出：

- 统一 `GatewayRequest`

边界：

- 不做业务策略
- 不做检测

### 6.3 输入解析模块

职责：

- 解析文本、JSON、XML、附件、OCR、转写内容
- 提取可检测文本和结构化字段

输入：

- 标准化请求

输出：

- 可检测内容
- 结构化字段
- 附件元信息

边界：

- 只负责“把内容变成可治理输入”
- 不决定内容是否高风险

### 6.4 敏感检测引擎

职责：

- 检测姓名、手机号、身份证、地址、银行卡、代码 secrets、业务字段等
- 支持文本、结构化、附件、RAG 片段检测

输入：

- 解析后的内容
- 规则与上下文

输出：

- 统一敏感实体列表
- 置信度和命中规则

边界：

- 只负责识别，不直接决定阻断还是放行

### 6.5 脱敏引擎

职责：

- 根据策略执行：
  - 掩码替换
  - 部分保留
  - 泛化
  - 占位符替换

输入：

- 原始内容
- 敏感实体
- 策略动作

输出：

- 脱敏后的内容

边界：

- 只修改内容
- 不负责最终策略选择

### 6.6 风险决策引擎

职责：

- 综合身份、场景、数据等级、目标模型和命中结果做动作决策

可输出动作：

- `ALLOW`
- `DESENSITIZE_AND_ALLOW`
- `ROUTE_TO_INTERNAL_MODEL`
- `BLOCK`
- `REQUIRE_APPROVAL`
- `ASYNC_REVIEW`

边界：

- 它是整个数据面的大脑
- 检测引擎只给证据，策略中心只给规则，决策引擎负责产出动作

### 6.7 模型路由模块

职责：

- 选择最终调用的模型和供应商
- 根据策略决定是否改走内部模型
- 处理故障切换和 fallback

边界：

- 只决定“调用哪里”
- 不负责脱敏和风险判断

### 6.8 输出审查模块

职责：

- 对模型输出再次做检测
- 防止回显敏感数据
- 防止越权内容输出

边界：

- 是输出侧安全闸门
- 不处理输入接入问题

### 6.9 审计日志模块

职责：

- 写入风险事件
- 记录策略命中、动作结果、路由结果、策略版本

边界：

- 审计日志模块负责“记录”
- 审计查询模块负责“看”

### 6.10 指标与告警模块

职责：

- 输出监控指标
- 生成高风险告警
- 支持接入 Prometheus / Alertmanager / SIEM

边界：

- 只负责观测和事件通知
- 不参与主业务决策

### 6.11 异步任务调度模块

职责：

- 处理大文件、批量任务、审批任务
- 统一任务状态和回调

边界：

- 不处理普通同步聊天请求

## 7. 外部模型适配层边界

这一层负责屏蔽不同模型厂商差异。

### 7.1 LLM Provider Adapter

职责：

- 统一调用 OpenAI、DeepSeek、Qwen、豆包、内部私有模型
- 屏蔽不同请求协议和响应格式差异

边界：

- 只适配协议
- 不嵌入业务风险逻辑

### 7.2 模型能力目录

职责：

- 记录模型能力标签，例如：
  - 是否外部模型
  - 是否支持流式
  - 是否允许某类场景调用
  - 成本等级

边界：

- 提供模型元信息
- 不代替策略引擎做判断

## 8. 基础设施层边界

基础设施层为控制面和数据面提供运行支撑。

### 8.1 数据存储

包括：

- 策略库
- 规则库
- 应用注册库
- 审计库
- 配置库

### 8.2 缓存与消息

包括：

- Redis
- MQ

用途：

- 配置缓存
- 审计异步写入
- 大文件任务队列

### 8.3 搜索与分析

包括：

- Elasticsearch / OpenSearch

用途：

- 审计检索
- 风险事件分析

### 8.4 监控设施

包括：

- Prometheus
- Grafana
- Alertmanager

### 8.5 文件与对象存储

包括：

- MinIO / OSS / S3

用途：

- 存储异步附件处理结果
- 存储局部脱敏后的审计样本

## 9. 模块交互边界图

```text
接入层
  -> 接入认证模块
  -> 请求标准化模块
  -> 输入解析模块
  -> 敏感检测引擎
  -> 风险决策引擎
      -> 脱敏引擎
      -> 模型路由模块
      -> 异步任务调度模块
  -> 输出审查模块
  -> 响应返回

并行支撑：
  -> 审计日志模块
  -> 指标与告警模块

控制面只做：
  -> 规则下发
  -> 策略下发
  -> 模型配置下发
  -> 应用与权限下发
```

## 10. 当前项目到目标模块的映射

### 10.1 已有模块可演进映射

- `GatewayController`
  - 目标：接入兼容层 / 通用网关入口

  - 目标：企业版统一网关入口，数据面核心编排
- `entity/gateway/*`
  - 目标：统一网关协议（请求/响应/风险决策/审计事件）
- `LlmProxyService`
  - 目标：数据面编排核心的一部分
- `DesensitizationManager`
  - 目标：输入治理与脱敏编排核心的一部分
- `SensitiveDetection/*`
  - 目标：敏感检测引擎
- `LlmClient/*`
  - 目标：外部模型适配层
- `SensitiveRuleService` + `SensitiveDictController` + `DictConfigService`
  - 目标：规则中心 + 词典管理底层能力
- `plugin/`
  - 目标：浏览器插件接入层（当前为发送前检查模式，目标演进为请求重定向模式）

### 10.2 当前缺失的目标模块

- 策略中心
- 应用接入中心
- 风险决策引擎
- 输出审查模块的企业化策略能力
- 审计查询中心
- 指标与告警中心
- 异步任务调度模块
- 模型能力目录

### 10.3 当前不应继续扩大的模块

- `LlmDesensitization.vue`
  - 不应再作为主产品入口
- `DesensitizationManager`
  - 不应继续堆更多跨层决策逻辑
- `LlmProxyService`
  - 不应继续把编排、策略、路由、审计混在一个类中

## 12. 演进顺序建议

### 12.1 第一步：先立边界，不先拆部署

先在单体内完成逻辑拆层：

- 接入层
- 编排层
- 检测层
- 决策层
- 适配层
- 审计层

原因：

- 先稳定职责边界
- 再考虑是否拆成微服务

### 12.2 第二步：把控制面与数据面逻辑分离

即便还部署在一个进程里，也要先做到：

- 控制面接口与在线流量接口分开
- 配置写入与在线读取分开

### 12.3 第三步：引入异步任务和审计中心

优先解决：

- 附件场景
- 审计可查
- 风险事件沉淀

### 12.4 第四步：再考虑集群化和高可用

包括：

- 网关无状态化
- 策略缓存
- 审计异步化
- MQ 和对象存储接入

## 13. 比赛答辩建议怎么讲这张架构图

如果用于比赛答辩，不建议从代码类名开始讲，而建议按下面顺序讲：

1. `入口`
   - 浏览器插件、业务系统、Agent 平台都统一接入网关
2. `控制面`
   - 策略、规则、应用和审计统一管理
3. `数据面`
   - 输入解析、敏感检测、脱敏、阻断、路由、输出审查
4. `模型层`
   - 可同时对接外部模型和内部私有模型
5. `价值`
   - 实现统一治理、统一审计、统一控制

一句话总结这张架构图：

- `这不是一个脱敏展示网站的架构图，而是一套企业 AI 调用治理平台的目标架构图。`

## 14. 结论

企业版目标架构的关键不在于“模块越多越好”，而在于边界明确：

- 控制面负责治理
- 数据面负责执行
- 接入层负责导流
- 适配层负责连模型
- 基础设施层负责支撑

对当前项目而言，最重要的不是立刻把系统拆成很多服务，而是先把这些模块边界在代码和文档层面立起来。

只有边界稳定后，后面的：

- 网关化
- 平台化
- 集群化
- 企业部署

才会真正可落地。
