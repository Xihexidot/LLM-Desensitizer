
## 3. 企业为什么需要它

企业真正担心的不是“能不能调通 LLM”，而是下面这些风险：

- 员工把客户手机号、身份证、合同、病历、财务数据直接粘贴给外部模型
- 内部系统调用大模型接口时，将生产数据、工单数据、源码、数据库字段直接发出

- 大模型响应中回显敏感信息、内部知识、账号标识或命中合规红线

- 无法追踪是谁、在什么场景下、把什么数据发给了哪个模型
- 无法统一限制哪些业务可以调用外部模型，哪些只能走私有模型
- 无法证明企业已经做过“数据最小化、脱敏、审计留痕、越权防护”

因此，一个企业级方案必须同时满足：

- `安全`：识别和阻断高风险内容
- `合规`：留痕、审计、分级分类、策略可解释
- `可控`：统一接管模型出口，不让业务系统各自直连
- `可运维`：能看指标、日志、命中率、失败率、策略效果
- `可集成`：能接 API、插件、网关、Agent 平台、RAG 平台

## 4. 真实应用场景

### 4.1 员工直连大模型场景

典型场景：

- 客服、法务、HR、运营、销售、研发直接使用 DeepSeek、OpenAI、豆包、通义千问等工具

常见风险：

- 粘贴用户手机号、身份证、订单号、病历、聊天记录
- 粘贴公司内部制度、未发布方案、招投标文件、报价单
- 把源代码、接口文档、数据库表结构发给外部模型

推荐落地方式：

- 浏览器插件或桌面代理把请求改发到企业 AI 安全网关
- 网关对输入做检测、脱敏、策略判定
- 风险低则放行到模型
- 风险高则阻断、打标、审批、改走私有模型

这个场景下，当前项目里的：

- `plugin/`
- `GatewayController`
- `LlmProxyService`

都可以继续演进，但要从“演示插件 + 演示代理”升级成“企业统一出口控制”。

### 4.2 业务系统调用大模型 API 场景

典型场景：

- CRM、工单系统、客服机器人、知识问答系统、营销文案系统调用大模型 API

常见风险：

- 程序员直接把生产数据对象序列化后发送给模型
- RAG 检索结果里带出客户明文信息
- 业务接口绕过安全层，直接访问外部模型

推荐落地方式：

- 所有业务系统不得直连外部 LLM
- 统一通过企业内部 LLM Gateway 调用
- 网关接收标准化请求，执行输入检测、脱敏、输出检查、审计记录

这个场景下，项目应该重点强化：

- OpenAI 兼容网关协议
- 统一认证鉴权
- 租户/应用/环境隔离
- 调用配额和策略路由

### 4.3 数据分析与报表生成场景

典型场景：

- 用大模型分析 Excel、PDF、工单报表、日志、医疗记录、客服记录

常见风险：

- 上传的文件中直接包含姓名、手机号、地址、银行卡、病例号、合同编号
- 文件解析后内容量大，风险实体多，单次检测开销高

推荐落地方式：

- 文件先进入“解析与预处理服务”
- 结构化抽取后进入敏感检测流水线
- 高风险文档进入异步任务和人工复核队列
- 低风险文档走同步脱敏 + 模型调用

这个场景说明：

- 企业版不能只支持文本输入
- 必须支持 `文本 + 结构化数据 + 附件 + 批处理 + 异步任务`

### 4.4 RAG / 知识库问答场景

典型场景：

- 企业内部知识库、制度库、工单知识、项目文档、代码知识库接入 RAG

常见风险：

- 检索出的 chunk 本身带敏感字段
- prompt 模板拼接时把用户、部门、账号等上下文一并发送
- 模型返回时重新组合出本不应暴露的信息

推荐落地方式：

- 在 RAG 的两个位置接入安全层
- 检索结果回注前做内容过滤
- 最终 prompt 发出前再做一次检测/脱敏
- 最终回答返回前再做输出审查

这个场景下，产品应支持：

- 检索片段级风险标记
- 数据源标签透传
- 输出溯源

### 4.5 Agent 与自动化流程场景

典型场景：

- 企业内部 Agent 自动读工单、调用接口、读取知识库、生成回复、写回系统

常见风险：

- Agent 会组合多源上下文，比单次聊天更容易触发数据泄露
- 工具调用参数和返回值都可能含敏感数据

推荐落地方式：

- 在 Agent Runtime 和 Tool 调用层接入安全代理
- 不只是保护“prompt 文本”，还要保护：
  - tool input
  - tool output
  - memory
  - intermediate reasoning context

这时产品已经不只是“聊天安全网关”，而是“AI 工作流安全中间件”。

## 5. 企业级产品应采用的部署形态

### 5.1 最推荐形态：统一 AI 安全网关

```text
用户 / 浏览器插件 / 业务系统 / Agent 平台
    -> 企业 AI 安全网关
        -> 输入解析
        -> 敏感检测
        -> 脱敏 / 阻断 / 审批 / 路由
        -> 大模型调用
        -> 输出审查
        -> 审计留痕
    -> 外部 LLM / 内部 LLM
```

优点：

- 接入位置统一
- 策略统一
- 审计统一
- 最符合企业治理需求

适用：

- 企业已有多个系统调用大模型
- 需要统一治理供应商、密钥、调用策略


## 6. 企业版目标架构

如果面向企业落地，建议将当前项目演进为“控制面 + 数据面”两部分。

### 6.1 控制面

控制面负责管理，不直接承载高频数据流量。

包含：

- 策略管理
- 规则管理
- 敏感类型字典管理
- 应用接入管理
- 租户与部门隔离
- 供应商配置管理
- 仪表盘与审计查询
- 灰度发布与策略版本管理

可理解为当前前端和部分后台管理接口的企业化升级。

### 6.2 数据面

数据面负责真正处理在线请求。

包含：

- 请求接入层
- 输入标准化层
- 内容解析层
- 检测引擎
- 脱敏引擎
- 风险决策引擎
- 模型路由层
- 输出审查层
- 日志与指标采集

### 6.3 参考架构图

```text
                    [控制面]
  策略管理 / 规则管理 / 租户管理 / 审计查询 / 配置中心
                          |
                          v
                    [策略下发中心]
                          |
-------------------------------------------------------------
                          |
                    [数据面网关集群]
     接入认证 -> 解析 -> 检测 -> 脱敏 -> 决策 -> LLM路由 -> 输出审查
                          |
          -----------------------------------------
          |                   |                   |
          v                   v                   v
      外部 OpenAI         外部 DeepSeek        内部私有模型
```

## 7. 企业版核心能力清单

### 7.1 输入安全能力

- 文本检测
- JSON/XML/表单检测
- 文件解析和文件内容检测
- OCR/语音识别接入能力
- Prompt 模板变量检测
- RAG 检索片段检测

### 7.2 输出安全能力

- 模型输出回显检测
- 敏感字段恢复控制
- 高风险回答阻断或替换
- 输出分级打标

### 7.3 风险决策能力

不是所有命中都一律脱敏，企业要的是策略控制：

- 允许通过
- 自动脱敏后通过
- 拒绝调用
- 进入审批流程
- 进入人工复核

决策维度包括：

- 调用应用
- 用户身份
- 部门
- 数据分级
- 场景类型
- 模型供应商
- 是否出境
- 是否命中高危规则

### 7.4 审计与合规能力

必须支持：

- 谁调用了哪个模型
- 输入命中了哪些敏感类型
- 是否执行了脱敏
- 是否被阻断
- 最终路由到哪个模型
- 输出是否再次命中风险
- 完整策略版本号

注意：

- 审计日志本身不能直接保存完整明文敏感数据
- 日志应该保存摘要、标签、哈希、局部脱敏后的样本

### 7.5 运维能力

- QPS、TP99、错误率
- 各类敏感命中率
- 各应用风险排行
- 模型调用成本统计
- 规则误报漏报分析
- 网关节点健康与扩缩容

## 8. 具体业务场景下的策略示例

### 8.1 客服场景

输入：

- 用户咨询记录
- 订单详情
- 手机号、收货地址、售后问题

策略建议：

- 手机号、身份证、详细地址默认部分脱敏
- 工单编号允许保留
- 命中银行卡、支付密码、身份证照片描述时直接阻断
- 外部模型不允许接收完整订单明细，可改走内部模型

### 8.2 医疗场景

输入：

- 病历摘要
- 检查报告
- 患者姓名、身份证号、病案号

策略建议：

- 患者姓名、身份证、手机号、地址强制脱敏
- 病种、科室、诊断标签允许保留
- 原始病历附件必须异步处理
- 输出阶段再次检查是否回显个人标识信息

### 8.3 金融场景

输入：

- 客户基本信息
- 交易记录
- 银行卡号、证件号、账户号

策略建议：

- 外部模型默认禁止接收完整交易流水
- 高等级客户数据只允许调用内网模型
- 命中银行卡、账户号、验证码类信息直接阻断
- 审计日志保留摘要而非原文

### 8.4 研发场景

输入：

- 源代码
- SQL
- 配置文件
- 日志

策略建议：

- API Key、数据库连接串、Token、内网地址强制脱敏
- 生产库表名、客户表字段打标告警
- 允许将代码片段发送到指定模型，但必须经过安全网关
- 对上传文件和粘贴内容统一执行 secrets scanning

### 8.5 政务与公共服务场景

输入：

- 群众申报信息
- 身份信息
- 地址、电话、审批材料

策略建议：

- 涉及证照号、住址、联系方式时强制脱敏
- 不允许外部模型保留可追溯个人标识
- 输出必须可审计和可留档

## 11. 关键设计原则

企业落地时，建议坚持以下原则：

### 11.1 网关优先，不要页面优先

真正的企业价值来自“统一接管调用链”，不是“做一个好看的演示页”。

### 11.2 策略优先，不要模型优先

企业最关心的是：

- 什么数据能出去
- 什么时候必须脱敏
- 什么情况必须阻断

而不是先接多少个模型。

### 11.3 审计优先，不要只看功能跑通

企业最终会问：

- 你怎么证明已经做了保护
- 事故发生后怎么追踪
- 谁改过规则

所以审计必须从一开始就纳入设计。

### 11.4 可灰度优先，不要一次性替换

企业系统复杂，不能要求所有业务“一次性切换”。

更合理的方式是：

- 先旁路观察
- 再灰度脱敏
- 再开启阻断
- 最后变成默认强制入口

### 11.5 情景感知是增强项，不是信任根

情景感知可以帮助：

- 缩小检测范围
- 调整策略
- 优化误报

但它不应成为“是否安全”的唯一依据，因为它天然不稳定。

## 12. 最终建议结论

如果以企业部署为目标，这个项目未来最合理的形态不是：

- “一个展示敏感识别和脱敏效果的网站”

而应该是：

- “一个统一治理企业大模型调用的 AI 安全网关”

最核心的使用方式也不应该是：

- 员工手工打开网页输入内容

而应该是：

- 浏览器插件接入
- 业务系统 API 接入
- Agent / RAG / 工作流平台接入
- 统一网关转发与审计

一句话概括：

- `展示站点` 只是产品原型
- `AI 安全网关 + 策略控制台 + 审计平台` 才是企业级落地方向

## 14. 关键问题补充说明

这一节补充 4 个在企业落地时非常关键、也是当前方案经常会被问到的问题。

### 14.1 浏览器插件到底怎么拦截请求

当前项目里浏览器插件采用"发送前输入检查"模式：

1. 用户仍然在原始 AI 网站中操作，正常输入文本
2. 用户点击发送或按 Enter 时，插件 `content.js` 截获发送事件和输入内容
3. 插件将输入文本发送到本地后端 `/desensitize/text` 做敏感检测
4. 后端返回检测结果，插件 `popup.js` 弹出安全检测弹窗
5. 用户可选择"发送脱敏版"、"发送原文"或"取消"

企业落地演进方向上，更推荐的模式是将插件升级为请求重定向模式：

1. 用户仍然在原始 AI 网站中操作
2. 浏览器插件识别指定模型请求
3. 插件把请求目标地址改写到企业网关
4. 企业网关接收后执行检测、脱敏、决策和转发
5. 网关返回兼容原站点的响应格式

这种方式比直接用 `nginx` 反向代理更实用，原因在于很多消费级 AI 网站并不只是普通 HTTP 接口，而是依赖：

- `Origin/Referer/Host` 校验
- `Cookie` 和登录态
- `CORS/CSP/CSRF` 策略
- 流式响应、SSE、WebSocket
- 页面脚本中的会话校验和风控逻辑

所以，很多时候不是代理“转不过去”，而是：

- 前端不接受代理后的响应
- 安全策略判定来源异常
- 鉴权链路在中间被打断

因此，更推荐的企业方案是：

- `浏览器插件负责入口接管`
- `企业网关负责实际安全控制`

而不是把 `nginx` 反向代理当成主要落地路径。

不过也要强调：

- 浏览器插件适合“员工直接使用网页 AI 工具”的场景
- 它不是企业级产品的唯一入口
- 真正的企业核心仍然应该是统一 AI 安全网关

更完整的接入优先级建议为：

1. `统一 API 网关接入`，面向业务系统
2. `浏览器插件接入`，面向员工网页使用
3. `Sidecar / 本地代理`，面向微服务和 K8s
4. `SDK 接入`，作为补充

### 14.2 真实使用场景的在线处理全流程

企业最关心的问题不是“能不能识别敏感信息”，而是：

- 员工误传了怎么办
- 系统到底能不能拦
- 是只能审查，还是能在线处理

答案取决于系统部署位置：

- 如果请求真正经过企业网关，就可以在线拦截、脱敏、阻断和审计
- 如果只是事后收集日志，就只能旁路审查

推荐的企业级在线处理流程如下：

```text
员工 / 插件 / 业务系统 / Agent
  -> 企业 AI 安全网关
  -> 鉴权与应用识别
  -> 请求标准化
  -> 输入解析
  -> 敏感检测
  -> 风险决策
     -> 放行
     -> 自动脱敏后放行
     -> 改走内部模型
     -> 阻断
     -> 人工审批 / 人工复核
  -> 调用目标模型
  -> 输出审查
  -> 审计留痕
  -> 返回结果
```

以“员工误把客户信息发给外部模型”为例：

1. 员工在网页、插件或业务系统中输入内容
2. 请求先进入企业网关
3. 网关识别出姓名、手机号、身份证、地址、订单号等实体
4. 策略引擎根据应用、部门、数据等级、模型类型做判断
5. 系统决定：
   - 低风险：脱敏后通过
   - 中风险：改走内部模型
   - 高风险：直接阻断
6. 模型返回结果后，再检查输出是否回显敏感信息
7. 最终结果和策略命中情况写入审计日志

所以，企业版产品不应只是“审查平台”，而应支持 4 种工作模式：

- `观察模式`
  - 只记录，不拦截
- `告警模式`
  - 提示风险，但先允许通过
- `自动脱敏模式`
  - 系统修改后再放行
- `阻断模式`
  - 命中高危规则直接拒绝

企业上线建议顺序也应该是：

1. 先观察
2. 再自动脱敏
3. 最后只对高危内容启用阻断

这样最符合真实企业的灰度落地方式。

### 14.3 情景感知不应再按旧方式定义

当前项目里保留的“情景感知”设计，本意是好的：

- 根据业务场景调整检测范围
- 根据上下文优化误报

但如果仍沿用“自己定义几个固定场景，然后让系统去猜”的方式，会有几个明显问题：

- 难以解释
- 稳定性差
- 容易误判
- 企业不容易信任

因此，企业落地时不建议再把它作为“情景感知主判断系统”，而建议把它重构成：

- `策略上下文`
- `风险上下文`
- `业务上下文驱动的策略决策`

也就是说，优先让上下游系统明确传入上下文，而不是让系统凭空猜。

推荐的上下文字段包括：

- `appId`
- `userId`
- `userRole`
- `department`
- `sceneCode`
- `dataClassification`
- `knowledgeBaseId`
- `channel`
- `destinationModel`
- `isExternalModel`

然后将旧的“情景感知”改造成 4 层判断模型：

1. `显式业务上下文`
   - 上游系统直接传入，可信度最高
2. `数据标签与资源标签`
   - 数据来自 CRM、病历库、代码仓库、RAG 等
3. `规则推断`
   - 通过命中字段、关键词、数据源标签辅助判断
4. `LLM / 模型推断`
   - 只作为增强项，不作为最终信任根

结论是：

- 情景感知可以继续保留
- 但不应再作为“是否安全”的唯一判断依据
- 它更适合成为策略引擎的辅助输入

换句话说，企业版不应该强调：

- “系统自动猜出这是医疗/金融/法律”

而应该强调：

- “系统结合业务上下文和数据上下文，动态选择更合适的治理策略”

### 14.4 市场竞争与参赛差异化

如果拿这个项目去参赛，不能只把竞争对象理解成“和你一样做网页脱敏演示的人”，而应该从 4 类产品看市场。

第一类是传统 DLP / 数据安全治理产品，例如：

- Microsoft Purview
- Symantec DLP
- Forcepoint DLP
- Nightfall AI
- Cyberhaven

这类产品的优势在于：

- 合规和治理体系成熟
- 覆盖邮件、Office、SaaS、浏览器、终端等多种渠道
- 企业部署经验强

其中 Microsoft Purview 已经把生成式 AI、Copilot 和企业 AI 应用纳入数据安全治理能力中。[Microsoft Purview 文档](https://learn.microsoft.com/en-us/purview/ai-microsoft-purview)

第二类是 AI 安全 / Prompt 安全 / Agent 安全产品，例如：

- Lakera
- Prompt Security
- Protect AI
- Palo Alto Prisma AIRS
- Aim Security

这一类更关注：

- Prompt injection
- Agent tool misuse
- LLM 调用链安全
- AI 应用攻击面治理

近两年这一方向增长很快，很多安全厂商都在通过并购快速布局。[CRN 2025 AI 安全工具盘点](https://www.crn.com/news/security/2025/the-10-hottest-ai-security-tools-of-2025)

第三类是隐私脱敏与 PII 检测 API 产品，例如：

- Private AI
- Skyflow
- Google Cloud DLP
- Microsoft Presidio

这类更像是底层能力组件，和本项目的检测/脱敏引擎层更接近。

第四类是国内大厂的大模型安全治理能力：

- 通常融入云安全、数据安全、大模型平台或政企 AI 平台中
- 不一定以单独开源项目形式存在

因此，参赛时不建议讲“我们要和所有安全大厂正面对打”，而建议聚焦以下差异化：

#### 差异化 1：不是展示页，而是企业 AI 网关原型

重点讲：

- 统一入口
- 统一治理
- 统一审计

#### 差异化 2：聚焦中文企业数据场景

例如：

- 中文姓名
- 身份证
- 手机号
- 地址
- 工单
- 合同
- 病历
- 政务材料
- 研发 secrets

#### 差异化 3：输入输出双向治理

不是只看用户输入，还看：

- 模型输出是否回显敏感信息
- RAG 检索片段是否越权
- Agent 工具调用是否带出敏感内容

#### 差异化 4：支持本地化 / 私有化部署

这对以下场景尤其重要：

- 政务
- 医疗
- 金融
- 高校
- 国企

#### 差异化 5：多入口统一接入

支持：

- 浏览器插件
- OpenAI 兼容 API 网关
- 业务系统 API
- Agent / RAG / 工作流平台

参赛时最合适的一句定位话术可以是：

- `我们不是做一个聊天页面的脱敏展示，而是在做一个面向企业 AI 使用全链路的数据安全网关。`

如果用于比赛答辩，建议重点演示的不是很多散点功能，而是一个完整闭环：

1. 员工或业务系统调用 AI
2. 请求先进入你们的安全网关
3. 系统识别并命中敏感信息
4. 按策略自动脱敏或阻断
5. 请求被转发到外部或内部模型
6. 返回结果前再次审查
7. 审计控制台展示命中规则、策略决策和结果

这个闭环比单纯展示“识别了多少手机号”更有产品和落地价值。
